## First protected migration: bounded side-effect proof

The objective is to avoid adding a duplicate supplier request or losing a local procurement during the transition; it is not a claim that all historical supplier accounting is correct. Historical ambiguous effects remain reconciliation cases. Do not restore an older database, reset the queue, change a supplier account/reference, or resubmit version-0 procurements to make the migration appear clean.

Source call chain at the integrated revision:

- `internal/modules/payment/application/payment_service_callback_dispatch.go:115` creates procurement after payment; `internal/modules/procurement/application/create.go` persists the procurement before `enqueuePending` can enqueue it. `RetryManual` is the other enqueue producer.
- `internal/queue/client.go:161` enqueues `procurement:submit` on the `default` queue. Options can override it, but the current procurement queue adapter supplies no overrides. `BuildServerConfig` also permits configured worker queue sets; a deployment must inventory all actual workers/Redis DBs/queues rather than assume one process.
- The only production call to `SubmitToUpstream` is `internal/app/jobs/consumer/consumer_upstream.go:41`. It reaches `application/submit.go:116`, `infrastructure/upstreamgateway/gateway.go:64`, and the fixed supplier adapter POST. Local order creation and PayPal checkout are separate operations and must not be confused with this procurement supplier path.
- The normal procurement repository has no delete operation; the domain relationship requests `OnDelete:NO ACTION`. The secure-store backfill only changes payload encryption. This source audit does not authorize external SQL cleanup, DB restores, or unreviewed scripts; they must remain fenced during the transition. Review all procurement rows including soft-deleted rows and terminal states when assessing unresolved effects, not just an active-status count.

A queue pause alone is insufficient. The consumer discards its cancellation context, the old submission uses `context.Background()` with a 30-second timeout, and jobs `Stop` ignores its argument and calls Asynq shutdown. The pinned Asynq default shutdown wait is 8 seconds. Zero active queue entries therefore does not by itself prove no old process can still issue/finish a POST.

The first migration needs independently verified closure of old API/payment callback/manual-retry producers and every old worker/scheduler, prevention of automatic restart, and confirmation that their processes and children cannot issue further requests. Then take a consistent live-DB snapshot. A snapshot containing only known receipt-bearing procurements is a useful finite transition precondition, but an earlier accepted/fulfilled count is not a substitute for the stopped-state read. The protected versions enforce a global local-order unique index including soft-deleted history; startup refuses duplicate groups without rewriting them. Review stopped-state all-row duplicate/soft-delete counts, and never remove history to satisfy the gate. Unknown rows are preserved and never automatically promoted to version 1. No timestamp-only or empty-queue inference licenses replay of a legacy pending row. New version-1 rows are created only by the protected code after the new writer epoch opens; stopping the old API avoids a gap that keeps creating unclassified version-0 rows.

If schema upgrade fails, keep old writers stopped and retain the live DB; diagnose and resume the same forward/additive migration rather than restore old data. If the candidate instance fails, recover only the exact protected baseline with the compatible schema and preserved intents/receipts/queue. Never enable b0 business writers after this transition. The full server bootstrap, all-process fencing, durable lifecycle supervisor and failure recovery still require their own proof; this fixture only exercises the actual procurement model migration and application compatibility. No production queue was paused and no quarantined supervisor probe was run.
