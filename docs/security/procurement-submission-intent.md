# Durable supplier submission intent and rollback compatibility

This change targets source baseline `b0b08aec6853b0d48a508af90ac852fc628e6982`. It does not deploy production, replay a purchase, or prove business rollback admission. It creates a new compatible application baseline for future releases to inherit.

## State and transaction boundary

New procurements carry `submission_version=1`. Before the only outbound purchase attempt, a transaction locks the root local order then its child, validates the current paid/fulfilling child and active parent lifecycle, and compare-and-sets pending/failed to submitted with a request SHA-256, supplier credential/endpoint identity SHA-256, and first-submission time. SQLite also obtains a writer reservation. The transaction commits before HTTP; duplicate workers cannot both claim it. No secret or manual form body is stored in these new fields.

Refunds take the same root-order lock and inspect root/child procurements in the refund transaction. Submitted/uncertain rows and unclassified legacy pending/failed/rejected rows block the refund. A committed refund prevents a subsequent submission claim. Partially delivered/refunded parent states remain valid for unaffected paid siblings; canceled, refunded, completed, delivered, pending-payment and unknown parent states do not authorize a purchase.

An unavailable, malformed, or negative supplier response is **not** proof of no charge. It leaves uncertainty, disables automatic and manual resubmission, and prevents cancellation or refund from hiding the unresolved effect. A failed local receipt write leaves submitted, which has the same protection after restart. No retry budget converts unknown acceptance to rejection. Local configuration/preparation errors before an outbound attempt remain distinguishable; legacy/previous-attempt guards run before those branches so they cannot incorrectly reject an existing remote effect. Authenticated callbacks for the generic Dujiao Next protocol retain their existing connection/downstream-order authorization and state-transition guards. NewZoe callbacks are explicitly rejected by the current ingress; NewZoe uncertainty cannot self-heal through that callback route. Known accepted receipts retain normal polling and fulfillment.

## Supplier evidence and manual reconciliation

The public NewZoe API documentation was fetched with an unauthenticated GET only on 2026-11-06: <https://shop.newzoe.cloud/docs/api/zh>. Local snapshot SHA-256: `933af79bb5df63b7830cfe25f4ce4cad1ff43f5a846538931103eb9130946b37`. It documents stable `Idempotency-Key`, HTTP 200 for replay of the same request, and conflict for a different body with the same key. It does not specify a 24-hour guarantee. The existing conservative age guard is not proof that any uncertain replay is safe. The adapter still uses its original stable key, but this change does not automatically replay an unresolved submission.

`GET /orders/{id}` needs the supplier receipt. `GET /account/orders` returns only the latest 20 orders; an absent result cannot prove no charge. Existing query contracts do not reliably bind all original product/SKU, quantity, dynamic supplier price/currency, and local request identity. A legitimate receipt from the same supplier account might belong to another customer. Therefore this change intentionally adds no automatic receipt-assignment endpoint and does not let an operator clear uncertainty merely by entering an order number.

The existing reconciliation job now records receipt-less submitted/uncertain purchases as unresolved status mismatches and uses its existing administrator notification; they are no longer silently skipped as if no comparison were needed. Resolving that review item does not mutate or unlock the procurement.

For submitted/uncertain rows: keep the order and payment state intact, record an external support case, preserve the local procurement ID, request digest, connection identity and timestamp, and obtain supplier evidence that identifies the exact original request and disposition. Do not create another purchase, cancel the local record, refund, clear Redis, or restore an older DB to make the blocker disappear. Existing authenticated generic-protocol callbacks or an already captured trustworthy receipt can use the existing lifecycle; this is not a callback recovery path for NewZoe. If no complete binding exists, the case remains visibly pending manual supplier reconciliation; a separately reviewed recovery procedure is required. This is an unresolved recovery limitation, not a completed business rollback test.

## Migration and safe rollback version floor

Schema additions are additive and default to version 0 for existing rows. Do not mass-mark legacy rows version 1. Existing accepted/fulfilled rows with their original receipts keep polling/delivery behavior. Parent task's read-only observation was one accepted and seven fulfilled receipts; that is a dated migration prerequisite, not permission to skip a fresh pre-deploy inventory. Legacy pending/failed/rejected rows require reconciliation and are blocked from blind retry/refund.

The new rollback floor is **b0b08ae plus this durable-intent protection**. Later security/cross-IP candidates must inherit the same schema, submitted/uncertain semantics and refund fence. A rollback between those compatible versions can preserve unresolved rows while continuing to refuse duplicate purchase and unsafe refund. It does not require uncertainty to disappear forever. The original b0b08ae binary lacks the refund/cancel guards and cannot be used as an enabled business-writer rollback target. Additive DB compatibility alone is insufficient. A candidate must prove this behavioral capability before admission, preserve the live DB and all intent rows, fence every HTTP/worker/scheduler writer before switching, and run fresh business and upstream checks. Existing production rollback refusal stays in place until that complete procedure is validated.

## Validation scope

Tests use temporary SQLite databases and local HTTP fixtures or replaced transports, never real supplier credentials or requests. Coverage includes response loss, receipt-write failure, fresh service reconstruction, one outbound claim under concurrent workers, real refund/submit races, root/child lifecycle, and legacy guards before missing-configuration branches. Normal accepted/fulfilled lifecycle and refund tests remain required, together with whole-repository compilation/tests. Administrator labels expose uncertainty and hide unavailable retry/cancel actions; backend guards are authoritative.

Local validation on the final worktree: `go test ./...` passed; procurement/order-refund/reconciliation suites passed with `-race`; related packages passed `go vet`. Administrator `vue-tsc -b`, Vite production build, and 62 tests across 11 files passed. The restart fixture persists its synthetic database and starts a new OS process that opens it read-only and verifies all three re-entry actions reject. The first full test run caught a stale architecture function-ownership list after removing unsafe retry helpers; the list was updated precisely and the full suite reran successfully. No architecture budget was increased.

## Local-order creation fence

A global unique index on `procurement_orders.local_order_id` includes soft-deleted history. Concurrent `CreateForOrder` calls cannot create independent submission claims. The existence read also includes hidden rows; hiding a legacy row never licenses a new version-1 purchase. Startup refuses duplicate local-order history before schema changes, without deleting or selecting a winner. The database index remains the final concurrent-insert boundary. First migration must preserve and review duplicate history if this gate rejects it; do not clean it automatically.
