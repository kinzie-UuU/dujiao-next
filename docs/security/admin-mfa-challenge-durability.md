# Admin MFA challenge durability

Administrator MFA challenge attempt and consumption state is stored in the primary database, not Redis. The additive `admin_2fa_challenges` table contains a SHA-256 JTI key, attempt count, consumed flag, and UTC expiry. It contains no OTP, password, recovery code or JWT. Expired records are removed on a subsequent attempt; records remain at least one minute beyond the maximum signed challenge lifetime.

Before checking an OTP/recovery code, a conditional atomic upsert reserves one of five attempts. A successful verification must atomically consume the challenge before issuing an access token. Concurrent requests cannot exceed five verification attempts or issue multiple sessions for the same challenge. Missing/unwritable storage returns a generic login failure and never bypasses MFA. Redis loss does not affect this state; restarting the process preserves it. Primary database failures still require database recovery, as with other account operations.

There is no account lock flag or password/MFA-setting change. A new password login creates a new challenge; exhausting a challenge does not lock the account. The purpose is versioned to `2fa_challenge_v2` so pre-migration Redis challenges cannot be replayed against empty database state. Someone mid-login during deployment must return to the password step once. Existing access tokens and ordinary non-MFA logins are unchanged. Rollback to the prior binary similarly requires restarting any in-progress new-version challenge and leaves the additive table harmlessly unused.

Tests use synthetic accounts and cover actual password → challenge → OTP/recovery login with Redis absent, retries after invalid codes, exhausted challenge/new login, stored state across store recreation, concurrent attempts/consume, storage write failure/recovery, cutover token validation, and existing access token parsing. TOTP test clocks are frozen to keep race instrumentation from expiring a real-time test code.

This change does not make recovery-code consumption and final session issuance one transaction. If a valid recovery code is consumed but the later database/session step fails, use another recovery code or TOTP and restart login if necessary. The pre-existing different-challenge concurrent recovery-code update behavior is outside this focused change; the single-challenge session guard is atomic.
